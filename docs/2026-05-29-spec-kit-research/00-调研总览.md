## 核心发现摘要

### Spec-Kit 是什么

GitHub 官方发布的**规范驱动开发（Spec-Driven Development, SDD）工具包**。核心主张是将规范（specification）从"代码的附属品"提升为"可执行的源文件"——规范生成代码，而非仅仅指导代码。

**技术栈**：Python CLI（`specify-cli`），通过 `uv` 安装。支持 30+ AI coding agent 集成。

**核心工作流**：`/speckit.constitution` → `/speckit.specify` → `/speckit.clarify` → `/speckit.plan` → `/speckit.tasks` → `/speckit.implement`

### OpenSpec 是什么

Fission-AI 发布的轻量规范框架。核心主张是"fluid not rigid"——无阶段门禁、工件随时可更新、适配棕地（brownfield）开发。

**技术栈**：Node.js/TypeScript CLI（`@fission-ai/openspec`），通过 npm 安装。支持 25+ AI assistant 集成。

**核心工作流（OPSX）**：`/opsx:propose` → `/opsx:apply` → `/opsx:archive`（或扩展模式：`/opsx:new` → `/opsx:continue` → `/opsx:ff` → `/opsx:apply` → `/opsx:verify` → `/opsx:archive`）

### 关键差异速览

| 维度 | Spec-Kit | OpenSpec |
|------|----------|----------|
| 哲学 | 宪法驱动、严格门禁 | 灵活迭代、工件驱动 |
| 流程 | 线性分阶段（有门禁） | 流式行动（无阶段锁定） |
| 规范风格 | 完整规范文档 | Delta 规范（增量变更） |
| 质量保障 | 9 条宪法条款 + Phase Gates | 渐进式严格度 + Schema 依赖 |
| 扩展 | Extensions（新增能力）+ Presets（定制模板） | Custom Schemas + Project Config |
| 适合场景 | 企业级、绿地项目、合规要求 | 棕地开发、快速迭代、多仓库 |

### 对现有 BMAD + OpenSpec 工作流的启示

1. **Spec-Kit 的 Constitution 机制**值得借鉴——为项目建立不可变原则，确保所有后续开发遵循统一标准。可在 OpenSpec 的 `config.yaml` 的 `context` / `rules` 字段中实现类似效果。
2. **Spec-Kit 的 Clarify 步骤**在 plan 之前做结构化澄清，减少下游返工。OpenSpec 的 `/opsx:explore` 有类似功能但更松散。
3. **OpenSpec 的 Delta Spec 模型**在棕地项目中远优于 Spec-Kit 的全量规范方式——每次只描述变更而非重写整体。
4. **不建议替换现有工作流**——两者哲学差异太大，强行混用会增加认知负担。现有 BMAD（规划）+ OpenSpec（实施）的分工已经成熟。
