# Epic 需求 QA 分析功能 - 需求分析

## 用户需求解读

**原始需求**: "帮我调研下github 上或者skill上是否存在，用于分析epic需求QA的功能，以供参考"

**需求分解**:
1. **Epic 需求**: 大型功能需求，通常需要多个迭代完成
2. **QA (问答)**: Question & Answer，问题与回答机制
3. **分析功能**: 对需求进行结构化分析和处理
4. **需求落地**: 从概念到实现的需求管理过程

**重点关注**: 需求、简易设计、提案草稿三个核心环节

## 现有解决方案分析

### OpenSpec 的需求管理能力

#### 1. 需求提案机制 (`/opsx:propose`)
```markdown
openspec/changes/{change-name}/
├── proposal.md          # 提案说明
├── specs/               # 需求规范
│   └── {category}/
│       └── spec.md
├── design.md            # 技术设计
└── tasks.md             # 实现任务清单
```

**优势**:
- 结构化的提案格式
- 自动生成需求文档模板
- 集成设计和实现规划

**局限**:
- 主要针对单一变更，缺少 Epic 级别的视图
- 没有专门的 QA 问答机制
- 需求探索功能较为基础

#### 2. 需求探索模式 (`/opsx:explore`)
```text
特点：
- 开放式对话探索
- 代码库调查能力
- 多方案比较分析
- 可视化图表支持
- 无结构约束
```

**适用场景**:
- 需求不明确时的前期调研
- 技术方案选型
- 架构决策分析

**局限性**:
- 临时性对话，不持久化
- 没有结构化的 QA 记录
- 缺少需求追溯机制

### Impeccable 的计划文档结构

#### 结构化计划模板
```markdown
# {feature-type}: {feature-title}

## Overview
## Problem Frame
## Requirements Trace
## Scope Boundaries
## Context & Research
## Key Technical Decisions
## Open Questions
## Output Structure
## High-Level Technical Design
## Implementation Units
## System-Wide Impact
## Risks & Dependencies
```

**优势**:
- 完整的需求追溯链
- 系统化的风险评估
- 清晰的决策记录
- 详细的实现分解

**可借鉴点**:
- 问题框架分析方法
- 需求到实现的映射
- 开放问题的追踪机制

## 功能空白分析

### 1. Epic 级别需求管理缺失

**现有问题**:
- OpenSpec 专注于单个变更，缺少 Epic 的宏观视图
- 没有 Epic 到具体任务的分解机制
- 缺少 Epic 级别的进度追踪

**需要的功能**:
```markdown
openspec/epics/
├── EPIC-001-user-authentication/
│   ├── epic.md              # Epic 概览
│   ├── requirements/        # 需求集合
│   ├── qa.md                # QA 记录
│   ├── changes/             # 关联的具体变更
│   └── timeline.md          # 时间线规划
```

### 2. 专门的 QA 问答系统缺失

**现有问题**:
- 探索模式提供问答但不持久化
- 没有结构化的问答记录格式
- 缺少问答到需求的追溯机制

**需要的功能**:
```markdown
## QA 记录结构

### 问题类别
- 功能澄清
- 技术选型
- 实现细节
- 边界条件
- 验收标准

### 问答格式
```yaml
questions:
  - id: Q001
    category: functional
    question: "如何处理用户离线状态？"
    answer: "使用本地存储 + 后台同步机制"
    asker: "product-manager"
    answerer: "tech-lead"
    timestamp: "2026-05-14"
    related_requirements: ["REQ-001", "REQ-002"]
```

### 3. 统一的文件分类和命名规范

**现有问题**:
- OpenSpec 有一定规范但不够完善
- Impeccable 使用不同的命名方式
- 缺少跨项目的一致性标准

## 推荐的文件分类结构

### Epic 级别结构
```
openspec/
├── epics/
│   ├── EPIC-{YYYYMMDD}-{id}-{name}/
│   │   ├── epic.md                 # Epic 总览
│   │   ├── qa.md                   # QA 问答记录
│   │   ├── requirements/           # 需求详情
│   │   │   ├── REQ-{id}-{desc}.md
│   │   │   └── ...
│   │   ├── design/                 # 设计文档
│   │   │   ├── DES-{id}-{component}.md
│   │   │   └── ...
│   │   ├── changes/                # 关联变更
│   │   │   └── ../../changes/{change-name}
│   │   └── timeline.md             # 实现时间线
├── changes/                        # 具体变更
│   └── {change-name}/
│       ├── .openspec.yaml
│       ├── proposal.md
│       ├── specs/
│       ├── design.md
│       └── tasks.md
└── specs/                          # 合并后的规范
    └── {category}/
        └── spec.md
```

### 命名规范

| 类型 | 格式 | 示例 |
|------|------|------|
| Epic | `EPIC-{YYYYMMDD}-{id}-{short-name}` | `EPIC-20260514-001-user-auth` |
| 需求 | `REQ-{id}-{description}` | `REQ-001-login-flow` |
| 设计 | `DES-{id}-{component}` | `DES-001-auth-component` |
| QA | `QA-{category}-{YYYYMMDD}` | `QA-functional-20260514` |
| 变更 | `{verb}-{noun}` | `add-login-button` |

## 需求追溯机制设计

### 1. Epic 到需求的追溯
```markdown
## Requirements Trace

| 需求 ID | 描述 | Epic | 状态 | 优先级 |
|---------|------|------|------|--------|
| REQ-001 | 用户登录功能 | EPIC-001 | 待实现 | P0 |
| REQ-002 | 密码重置 | EPIC-001 | 设计中 | P1 |
```

### 2. 需求到设计的追溯
```markdown
## Design Mapping

| 设计 ID | 关联需求 | 组件 | 状态 |
|---------|----------|------|------|
| DES-001 | REQ-001, REQ-002 | LoginForm | 审核中 |
```

### 3. 设计到实现的追溯
```markdown
## Implementation Tracking

| 变更名 | 关联设计 | 任务状态 | 负责人 |
|--------|----------|----------|--------|
| add-login-form | DES-001 | 开发中 | @dev1 |
```

## QA 问答系统设计

### QA 记录格式
```markdown
# QA Record: {Epic Name}

## Open Questions
### Q001: {Question Title}
- **Category**: {functional|technical|implementation}
- **Asked By**: {stakeholder}
- **Date**: {YYYY-MM-DD}
- **Status**: {open|answered|deferred}

**Question**: {详细问题描述}

**Context**: {问题背景}

**Answer**: {如果已回答}

**Related Requirements**: [{req-id-list}]

**Related Decisions**: [{decision-id-list}]

## Answered Questions
[已回答问题的历史记录]
```

### QA 工作流
```text
需求提出 → 问题识别 → QA 记录 → 专家回答 → 决策记录 → 需求更新
    ↓                                                    ↑
    └────────────────── 迭代澄清 ◄──────────────────────┘
```

## 技术实现建议

### 1. 扩展 OpenSpec 命令
```bash
/opsx:epic new <epic-name>        # 创建新 Epic
/opsx:epic explore <epic-id>      # 探索 Epic
/opsx:qa add <epic-id>            # 添加 QA 记录
/opsx:qa answer <qa-id>           # 回答问题
/opsx:trace <epic-id>             # 查看追溯链
```

### 2. 增强需求解析
- 支持自定义需求块格式
- Epic 级别的需求聚合
- 自动生成追溯关系

### 3. QA 管理工具
- 问题状态跟踪
- 自动提醒未回答问题
- 问题相似度检测
- 决策历史查询
