# OpenSpec 提案推理标注 Skill 调研总览

## 调研背景

本次调研旨在设计一个 **OpenSpec 提案推理标注 skill**（reasoning-annotate），核心目标是在 OpenSpec 生成提案产物时，标注出用户关心的高价值 AI 推理内容。标注依据用户与 AI 共同维护的分类表，以非阻断方式附加在 OpenSpec 流程之上。

**调研日期**: 2026-06-11
**调研范围**: CodeRef Vault skill-vault 内已有内容（guess-governance trait、openspec repo、impeccable skill 结构）
**调研重点**: OpenSpec 提案生成流程、guess-governance trait 模式、YAML 分类表设计、非阻断标注机制

## 调研发现

### 1. OpenSpec 提案生成流程（证据源）

**位置**: `repos/openspec/src/core/templates/workflows/propose.ts`

**关键流程**：
1. 用户输入 → 生成 kebab-case change name
2. `openspec new change "<name>"` 创建变更目录
3. `openspec status --change "<name>" --json` 获取 artifact 构建顺序
4. 逐个创建 artifact（proposal.md → design.md → tasks.md），每个 artifact 通过 `openspec instructions` 获取模板
5. AI 将 `context` + `rules` 作为约束，写入 `template` 结构，生成 `proposal.md`

**标注插入点分析**：
- `proposal.md` 生成完毕后 → 可追加标注 section（推荐）
- `design.md` 生成后 → 可标注设计推理
- 整个 propose 流程结束后 → 输出标注摘要（推荐）

**OpenSpec skill 模板结构**（`repos/openspec/src/core/templates/types.ts`）：
```typescript
interface SkillTemplate {
  name: string;
  description: string;
  instructions: string;
  license?: string;
  compatibility?: string;
  metadata?: Record<string, string>;
}
```

### 2. guess-governance Trait 模式分析（参考模板）

**位置**: `~/.claude/skills/guess-governance/skill.md`

**核心设计模式**：
- **YAML frontmatter**: name + description
- **适用范围声明**: "You operate under guess governance"
- **分类体系**: Domain instincts / Undefined-content levels / Delivery tiers
- **量化指标**: Guess Count / Guess Ratio / Guess Risk
- **行为护栏**: 明确的 Do/Don't 规则
- **过程模板**: triage → classify → choose tier → compute metrics
- **产物模板**: 嵌入 proposal.md 的 markdown 模板
- **阻断逻辑**: 带门控阈值的 governance check
- **阻断输出模板**: 结构化的 "When blocked" 输出

**本 skill 与 guess-governance 的关键区别**：
| 维度 | guess-governance | reasoning-annotate |
|------|-----------------|-------------------|
| 核心目标 | 控制假设风险 | 标注高价值推理 |
| 分类来源 | 内置固定分类 | YAML 文件，用户/AI 共同维护 |
| 阻断性 | 可阻断流程 | **不阻断**，纯标注 |
| 作用阶段 | propose/apply/archive 全程 | proposal.md 和 design.md |
| 量化指标 | Guess Ratio/Risk | 分类命中率、标注覆盖率 |

### 3. OpenSpec Skill 生态集成点

**已有 workflow skills**（`repos/openspec/src/core/shared/skill-generation.ts`）：
- explore、new-change、continue-change、apply-change
- ff-change、sync-specs、archive-change
- bulk-archive-change、verify-change、onboard
- **propose** ← 核心集成点

**Skill 安装方式**：
- `openspec init` 时自动安装到各 harness 的 `skills/` 目录
- 通过 `skill-generation.ts` 的 `generateSkillContent()` 生成 YAML frontmatter + instructions
- 注册到 `getSkillTemplates()` 数组中

**非 skill 集成方式（替代方案）**：
- 作为独立 skill 安装到 `~/.claude/skills/`（如 guess-governance）
- 通过 AGENTS.md 或 CLAUDE.md 中的指令触发
- 不修改 OpenSpec 源码，纯 skill 级别

### 4. YAML 分类表设计考量

**选择 YAML 而非 CSV 的理由**：
- 与 OpenSpec 生态一致（`config.yaml`、`AGENTS.md` 均为 YAML）
- 支持嵌套结构，便于按 domain 分组
- 天然支持注释（`#`），比 CSV 注释更友好
- AI 解析 YAML 比 CSV 更可靠（无需处理逗号转义、多行字段）
- 可直接嵌入 OpenSpec `config.yaml` 的 `rules` 体系或作为独立文件

**YAML 存放位置选项**：
| 位置 | 优点 | 缺点 |
|------|------|------|
| 项目级 `openspec/reasoning-categories.yaml` | 随项目版本控制，团队共享；与 OpenSpec 目录结构一致 | 需要每个项目配置 |
| 嵌入 `openspec/config.yaml` 的 `reasoning-categories` 字段 | 单文件管理，无额外文件 | config.yaml 职责膨胀 |
| 全局 `~/.openspec/reasoning-categories.yaml` | 一次配置，所有项目生效 | 不区分项目差异 |
| Skill 内置默认 + 项目级覆盖 | 有合理默认值，可定制 | 两层查找逻辑稍复杂 |

**推荐方案**：独立文件 `openspec/reasoning-categories.yaml`，与 OpenSpec config.yaml 同级目录。

**YAML 结构草案**：
```yaml
# 推理标注分类表
# 订阅的分类将在 OpenSpec 提案生成时被标注

domains:
  技术:
    arch-decision:
      name: 架构决策
      description: 涉及系统架构选择和权衡的推理
      priority: high
      subscribed: true
    security:
      name: 安全考量
      description: 安全相关的设计推理
      priority: high
      subscribed: true
    perf-impact:
      name: 性能影响
      description: 影响性能的设计选择推理
      priority: medium
      subscribed: true
    data-model:
      name: 数据模型
      description: 数据结构设计相关推理
      priority: medium
      subscribed: true
    integration:
      name: 集成风险
      description: 外部依赖和集成点相关推理
      priority: medium
      subscribed: true
    migration:
      name: 迁移策略
      description: 数据或系统迁移相关推理
      priority: low
      subscribed: true
    monitoring:
      name: 可观测性
      description: 日志、监控、告警相关推理
      priority: low
      subscribed: false

  业务:
    biz-rule:
      name: 业务规则
      description: 涉及业务流程、领域逻辑的推理内容
      priority: high
      subscribed: true
    ux-assumption:
      name: UX假设
      description: 关于用户体验的假设推理
      priority: medium
      subscribed: false

  通用:
    scope-decision:
      name: 范围决策
      description: 关于功能范围边界的推理
      priority: medium
      subscribed: true
```

**结构说明**：
- 顶层按 `domains` 分组（`技术`/`业务`/`通用`），与 OpenSpec config.yaml 的 `rules` 按字段分组风格一致
- 每个 domain 下为 flat map，key 为 `category_id`
- 每个分类包含 `name`、`description`、`priority`、`subscribed` 四个字段
- 支持完整 YAML 注释，便于维护

### 5. 非阻断标注机制设计

**设计原则**：
- 不修改 OpenSpec 的 `propose` 流程步骤
- 不改变 `proposal.md` 的必需结构
- 在 artifact 生成后追加标注 section
- 通过 skill description 的 auto-trigger 实现"寄生"激活

**标注策略：产物追加 Section（Strategy A）**

在 `proposal.md` 和 `design.md` 末尾直接追加 `## Reasoning Annotations` section。
- 优点：标注与产物绑定，可追溯，持久化
- 不需要用户确认，生成 artifact 后自动追加
- 重复标注时整体替换已有 section

标注完成后在会话中输出一行摘要通知。

## 研究结论

### 可行性评估

| 评估维度 | 结论 |
|---------|------|
| OpenSpec 集成可行性 | ✅ 高 — skill 级别非侵入式集成 |
| guess-governance 模式可复用 | ✅ 高 — trait 结构、分类体系、护栏模式直接参考 |
| YAML 分类表维护可行性 | ✅ 高 — YAML 与 OpenSpec config.yaml 风格一致，用户/AI 均可编辑 |
| 非阻断承诺 | ✅ 可保证 — 纯标注，不改 propose 流程 |

### 关键设计决策

1. **Skill 定位**：独立 skill，非 OpenSpec 内置，类似 guess-governance 的安装方式
2. **分类表格式**：YAML（`reasoning-categories.yaml`），与 OpenSpec config.yaml 风格一致，支持项目级覆盖全局默认
3. **标注策略**：直接追加 `## Reasoning Annotations` section 到 proposal.md 和 design.md
4. **触发方式**：auto-trigger description 检测到 propose 相关关键词
5. **不阻断**：始终只标注，不阻止任何 OpenSpec 步骤
6. **标注范围**：proposal.md 和 design.md（不含 spec.md、tasks.md）

### 是否需要为当前系统生成提取分类的方案

**建议：不需要独立的提取分类生成方案，原因如下**：
- YAML 分类表本身即是"分类方案"
- 初始分类可由 skill 内置默认提供
- 用户和 AI 可通过编辑 YAML 直接增减分类
- 如果需要更复杂的分类管理，可在后续迭代中添加 `/reasoning-annotate manage` 管理命令
