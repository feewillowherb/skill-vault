# 推理分类表 (reasoning-categories.csv) 规范

## 概述

推理分类表是 `reasoning-annotate` skill 的核心数据源。它定义了哪些类型的 AI 推理内容被视为"高价值"，以及用户当前订阅了哪些分类。

## CSV 格式规范

### 文件编码与格式

- 编码：UTF-8（支持中文内容）
- 分隔符：逗号 `,`
- 换行符：LF（Unix 风格）
- 第一行为表头（required）
- 空行忽略
- `#` 开头的行视为注释，忽略

### 字段定义

| 字段 | 类型 | 必填 | 描述 | 示例 |
|------|------|------|------|------|
| `category_id` | string | ✅ | 唯一标识符，kebab-case | `arch-decision` |
| `category_name` | string | ✅ | 显示名称，可中文 | `架构决策` |
| `domain` | enum | ✅ | 分类领域：`技术`/`业务`/`通用` | `技术` |
| `description` | string | ✅ | 分类描述，AI 匹配依据 | `涉及系统架构选择和权衡的推理` |
| `priority` | enum | ✅ | 优先级：`high`/`medium`/`low` | `high` |
| `subscribed` | boolean | ✅ | 是否订阅：`true`/`false` | `true` |

### 字段校验规则

```
category_id   : /^[a-z0-9][a-z0-9-]*$/  (小写字母、数字、连字符，不以连字符开头)
category_name : 1-50 字符
domain        : "技术" | "业务" | "通用"
description   : 1-200 字符，应清晰描述匹配条件
priority      : "high" | "medium" | "low"
subscribed    : "true" | "false" (区分大小写)
```

### domain 枚举说明

| 值 | 含义 | 适用场景 |
|----|------|---------|
| `技术` | 技术领域推理 | 架构、安全、性能、数据、集成等 |
| `业务` | 业务领域推理 | 业务规则、用户流程、合规、UX等 |
| `通用` | 跨领域推理 | 范围决策、优先级、依赖关系等 |

## 文件存放位置

### 优先级（高到低）

```
1. <project>/.openspec/reasoning-categories.csv     ← 项目级（最高优先级）
2. ~/.openspec/reasoning-categories.csv               ← 全局级
3. skill 内置默认                                      ← 兜底
```

**查找逻辑**：skill 每次激活时，按优先级顺序查找，使用第一个找到的文件。

### 项目级文件

推荐在 OpenSpec 项目根目录的 `.openspec/` 下创建：

```
my-project/
├── .openspec/
│   ├── config.yaml
│   └── reasoning-categories.csv    ← 项目级分类表
├── openspec/
│   └── changes/
└── ...
```

### 全局文件

```
~/.openspec/
└── reasoning-categories.csv        ← 全局默认分类表
```

## 内置默认分类表

当无任何 CSV 文件时，skill 使用以下内置默认值：

```csv
category_id,category_name,domain,description,priority,subscribed
arch-decision,架构决策,技术,涉及系统架构选择和权衡的推理,high,true
biz-rule,业务规则,业务,涉及业务流程、领域逻辑的推理,high,true
security,安全考量,技术,安全相关的设计推理,high,true
perf-impact,性能影响,技术,影响性能的设计选择推理,medium,true
data-model,数据模型,技术,数据结构设计相关推理,medium,true
integration,集成风险,技术,外部依赖和集成点相关推理,medium,true
ux-assumption,UX假设,业务,关于用户体验的假设推理,medium,false
scope-decision,范围决策,通用,关于功能范围边界的推理,medium,true
migration,迁移策略,技术,数据或系统迁移相关推理,low,true
monitoring,可观测性,技术,日志、监控、告警相关推理,low,false
```

### 默认分类设计理由

| 分类 | 为何默认订阅 | 为何设置此优先级 |
|------|------------|----------------|
| arch-decision | 架构决策影响全局，几乎总有价值 | high — 架构错误代价大 |
| biz-rule | 业务规则是需求核心 | high — 业务偏差直接影响交付 |
| security | 安全是不可妥协的底线 | high — 安全漏洞代价极高 |
| perf-impact | 性能常被忽略直到出问题 | medium — 值得标注但非阻断 |
| data-model | 数据模型变化成本高 | medium — 重要但专业性强 |
| integration | 集成点是常见故障源 | medium — 常见但非每个项目都关键 |
| ux-assumption | UX 假设需要验证但非所有项目适用 | medium, **未订阅** — 按需开启 |
| scope-decision | 范围蔓延是常见问题 | medium — 帮助追踪范围变更 |
| migration | 迁移策略在特定场景重要 | low — 不是每个提案都涉及 |
| monitoring | 可观测性是好的实践但非核心推理 | low, **未订阅** — 运维导向项目可开启 |

## 维护规则

### 用户手动维护

1. 直接编辑 CSV 文件
2. 修改 `subscribed` 列来开关分类
3. 添加新行来增加分类
4. 删除行来移除分类（谨慎操作，建议先设 `subscribed=false`）

### AI 辅助维护

**触发条件**：skill 检测到连续多次出现无法匹配的高价值推理

**AI 建议流程**：
1. 收集未匹配的推理段落
2. 分析是否形成模式（≥3 次同类推理 = 模式）
3. 如果形成模式，生成新分类建议
4. 展示给用户审批
5. 用户确认后才写入 CSV

**AI 建议模板**：

```csv
# AI suggested on <date> — <reason>
<suggested_id>,<suggested_name>,<domain>,<description>,<priority>,true
```

### 不允许 AI 自动修改

- AI 不得在没有用户明确确认的情况下修改 CSV
- AI 建议必须包含完整的行内容供用户审核
- 用户可以接受、修改后接受、或拒绝建议

## 示例：自定义项目分类

```csv
# 项目: fintech-payment-service
# 更新: 2026-06-11
#
category_id,category_name,domain,description,priority,subscribed
arch-decision,架构决策,技术,涉及系统架构选择和权衡的推理,high,true
biz-rule,业务规则,业务,涉及业务流程、领域逻辑的推理,high,true
security,安全考量,技术,安全相关的设计推理,high,true
compliance,合规要求,业务,涉及法规合规的推理（PCI-DSS、GDPR等）,high,true
payment-flow,支付流程,业务,涉及支付路由、清结算的推理,high,true
perf-impact,性能影响,技术,影响性能的设计选择推理,medium,true
data-model,数据模型,技术,数据结构设计相关推理,medium,true
idempotency,幂等性,技术,涉及操作幂等性保证的推理,medium,true
retry-strategy,重试策略,技术,涉及失败重试和补偿的推理,medium,true
ux-assumption,UX假设,业务,关于用户体验的假设推理,medium,false
monitoring,可观测性,技术,日志、监控、告警相关推理,low,true
```

此示例展示了金融支付项目的分类定制：新增了 `compliance`、`payment-flow`、`idempotency`、`retry-strategy`，将 `compliance` 和 `payment-flow` 设为 high 优先级。
