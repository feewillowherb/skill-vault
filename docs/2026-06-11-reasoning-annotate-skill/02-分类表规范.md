# 推理分类表 (reasoning-categories.yaml) 规范

## 概述

推理分类表是 `reasoning-annotate` skill 的核心数据源。它定义了哪些类型的 AI 推理内容被视为"高价值"，以及用户当前订阅了哪些分类。采用 YAML 格式，与 OpenSpec 的 `config.yaml` 保持一致的风格。

## YAML 格式规范

### 文件编码与格式

- 编码：UTF-8（支持中文内容）
- 换行符：LF（Unix 风格）
- 文件扩展名：`.yaml`（不使用 `.yml`）
- 缩进：2 空格（与 OpenSpec config.yaml 一致）
- `#` 开头的行为注释

### 文件结构

```yaml
# 推理标注分类表
# 订阅的分类将在 OpenSpec 提案生成时被标注
#
# 文档: reasoning-categories.yaml
# 维护者: 用户和 AI agent 共同维护

domains:
  技术:
    <category_id>:
      name: <display name>
      description: <matching criteria>
      priority: high | medium | low
      subscribed: true | false
      artifacts: proposal | design | both
      guess: true | false
  业务:
    <category_id>:
      name: <display name>
      description: <matching criteria>
      priority: high | medium | low
      subscribed: true | false
      artifacts: proposal | design | both
      guess: true | false
  通用:
    <category_id>:
      name: <display name>
      description: <matching criteria>
      priority: high | medium | low
      subscribed: true | false
      artifacts: proposal | design | both
      guess: true | false
```

### 字段定义

| 字段 | 类型 | 必填 | 描述 | 示例 |
|------|------|------|------|------|
| `domains` | map | ✅ | 顶层分组，key 为领域名称 | `技术` |
| `category_id` | string (key) | ✅ | 分类标识符，kebab-case | `arch-decision` |
| `name` | string | ✅ | 显示名称，可中文 | `架构决策` |
| `description` | string | ✅ | 匹配描述，AI 据此判断推理是否属于此分类 | `涉及系统架构选择和权衡的推理` |
| `priority` | enum | ✅ | 优先级：`high`/`medium`/`low` | `high` |
| `subscribed` | boolean | ✅ | 是否订阅：`true`/`false` | `true` |
| `artifacts` | enum | ❌ | 适用的产物类型：`proposal`/`design`/`both`。默认 `both` | `both` |
| `guess` | boolean | ❌ | 是否追踪推理的 Fact/Assumption/Mixed 依据。默认 `false` | `true` |

### 字段校验规则

```
domains key (domain name) : "技术" | "业务" | "通用"  (可扩展)
category_id              : /^[a-z0-9][a-z0-9-]*$/  (kebab-case)
name                    : 1-50 字符
description             : 1-200 字符
priority                : "high" | "medium" | "low"
subscribed              : true | false (YAML boolean)
artifacts               : "proposal" | "design" | "both" (可选，默认 "both")
guess                   : true | false (YAML boolean, 可选，默认 false)
```

### domain 枚举说明

| 值 | 含义 | 适用场景 |
|----|------|---------|
| `技术` | 技术领域推理 | 架构、安全、性能、数据、集成等 |
| `业务` | 业务领域推理 | 业务规则、用户流程、合规、UX等 |
| `通用` | 跨领域推理 | 范围决策、优先级、依赖关系等 |

用户可在 YAML 中添加自定义 domain，但 AI 应将未知 domain 归入"通用"汇总。

## 文件存放位置

### 优先级（高到低）

```
1. <project>/openspec/reasoning-categories.yaml   ← 项目级（最高优先级）
2. ~/.openspec/reasoning-categories.yaml            ← 全局级
3. skill 内置默认                                    ← 兜底
```

**查找逻辑**：skill 每次激活时，按优先级顺序查找，使用第一个找到的文件。

### 推荐目录结构

与 OpenSpec config.yaml 同级放置：

```
my-project/
├── openspec/
│   ├── config.yaml                      ← OpenSpec 项目配置
│   ├── reasoning-categories.yaml        ← 推理分类表（项目级）
│   ├── changes/
│   │   └── add-user-auth/
│   │       ├── proposal.md
│   │       ├── design.md
│   │       └── tasks.md
│   └── specs/
└── ...
```

### 全局文件

```
~/.openspec/
└── reasoning-categories.yaml            ← 全局默认分类表
```

### 与 OpenSpec config.yaml 的关系

分类表是独立文件，**不嵌入** config.yaml。原因：
- config.yaml 通过 Zod schema 校验（`ProjectConfigSchema`），添加自定义字段会破坏校验
- 独立文件可由非 OpenSpec 用户（纯 skill 用户）单独维护
- 职责分离：config.yaml 管 schema/context/rules，reasoning-categories.yaml 管标注分类

      priority: high
      subscribed: true
      artifacts: both
      guess: true
    perf-impact:
      name: 性能影响
      description: 影响性能的设计选择推理
      priority: medium
      subscribed: true
      artifacts: both

      priority: medium

    #   name: UX假设

### 默认分类设计理由

| 分类 | artifacts | guess | 为何默认订阅 | 为何设置此优先级 |
|------|-----------|-------|------------|----------------|
| arch-decision | both | true | 架构决策影响全局，几乎总有价值 | high — 架构错误代价大 |
| security | both | true | 安全是不可妥协的底线 | high — 安全漏洞代价极高 |
| biz-rule | both | true | 业务规则是需求核心 | high — 业务偏差直接影响交付 |
| tech-tradeoff | design | true | 技术方案对比是 design 核心推理 | high — 选错方案代价大 |
| capability-tradeoff | proposal | true | 能力取舍是 proposal 核心推理 | high — 决定交付范围 |
| perf-impact | both | true | 性能常被忽略直到出问题 | medium — 值得标注但非阻断 |
| data-model | both | true | 数据模型变化成本高 | medium — 重要但专业性强 |
| integration | both | true | 集成点是常见故障源 | medium — 常见但非每个项目都关键 |
| interface-decision | design | false | 接口设计是 design 阶段独有推理 | medium — proposal 不涉及实现细节 |
| implementation-strategy | design | false | 实现策略是 design 阶段独有推理 | medium — proposal 不涉及实现细节 |
| stakeholder-impact | proposal | false | 利益相关方影响是 proposal 阶段独有推理 | medium — design 侧重技术 |
| scope-decision | proposal | false | 范围蔓延是常见问题 | medium — 帮助追踪范围变更 |
| assumption-link | both | true | 推理基于未确认假设是高信号 | high — 未验证假设是风险源头 |
| migration | design | false | 迁移策略在特定场景重要 | low — 不是每个提案都涉及 |
| monitoring | — | — | 可观测性是好的实践但非核心推理 | low, **未订阅** — 运维导向项目可开启 |
| ux-assumption | — | — | UX 假设需要验证但非所有项目适用 | medium, **未订阅** — 按需开启 |

### artifacts 字段说明

分类按产物类型分组，解决 proposal.md 和 design.md 标注重合问题：

| artifacts 值 | 含义 | 分类示例 |
|-------------|------|---------|
| `proposal` | 仅标注 proposal.md | capability-tradeoff, stakeholder-impact, scope-decision |
| `design` | 仅标注 design.md | interface-decision, implementation-strategy, tech-tradeoff, migration |
| `both` | 同时标注两者（默认） | arch-decision, security, biz-rule, assumption-link |

省略 `artifacts` 字段时默认为 `both`，向后兼容 v1.0 YAML。

### guess 字段说明

轻量假设追踪，标注每条推理的 Fact/Assumption/Mixed 依据：

| guess 值 | 含义 | 标注效果 |
|---------|------|---------|
| `true` | 该分类的标注需检测 Fact/Assumption/Mixed | 标注包含 `**Basis**` 行 |
| `false` | 不检测（默认） | 标准标注格式 |

省略 `guess` 字段时默认为 `false`，向后兼容 v1.0 YAML。

## 维护规则

### 用户手动维护

1. 直接编辑 YAML 文件
2. 修改 `subscribed` 字段来开关分类
3. 在对应 domain 下添加新分类条目
4. 移除分类：删除该条目（建议先设 `subscribed: false`）

### AI 辅助维护

**触发条件**：skill 检测到连续多次出现无法匹配的高价值推理

**AI 建议流程**：
1. 收集未匹配的推理段落
2. 分析是否形成模式（≥3 次同类推理 = 模式）
3. 如果形成模式，生成新分类条目
4. 展示给用户审批
5. 用户确认后才写入 YAML

**AI 建议格式**：

```yaml
    # AI suggested on 2026-06-11 — 3 unmatched passages about retry logic
    retry-strategy:
      name: 重试策略
      description: 涉及失败重试和补偿的推理
      priority: medium
      subscribed: true
      artifacts: design
```

### 不允许 AI 自动修改

- AI 不得在没有用户明确确认的情况下修改 YAML
- AI 建议必须包含完整的条目内容供用户审核
- 用户可以接受、修改后接受、或拒绝建议

### YAML 编辑最佳实践

```yaml
domains:
  技术:
    # --- high priority ---
    arch-decision:
      name: 架构决策
      description: 涉及系统架构选择和权衡的推理
      priority: high
      subscribed: true
      artifacts: both
      guess: true

    security:
      name: 安全考量
      description: 安全相关的设计推理
      priority: high
      subscribed: true
      artifacts: both
      guess: true

    # --- medium priority ---
    perf-impact:
      name: 性能影响
      description: 影响性能的设计选择推理
      priority: medium
      subscribed: true
      artifacts: both
      guess: true

    # --- design exclusive ---
    interface-decision:
      name: 接口决策
      description: API/模块接口、函数签名、数据协议的设计选择推理
      priority: medium
      subscribed: true
      artifacts: design

    # --- 已禁用 ---
    # legacy-pattern:
    #   name: 遗留模式
    #   description: 识别遗留代码模式的推理
    #   priority: low
    #   subscribed: false
```

建议：
- 按 priority 分组注释，便于快速浏览
- 禁用的分类用注释包裹而非删除，便于恢复
- 每个分类前加简短注释说明用途

## 示例：自定义项目分类

```yaml
# 项目: fintech-payment-service
# 更新: 2026-06-11
#

domains:
  技术:
    arch-decision:
      name: 架构决策
      description: 涉及系统架构选择和权衡的推理
      priority: high
      subscribed: true
    security:
      name: 安全考量
      description: 安全相关的设计推理
      priority: high
      subscribed: true
    compliance:
      name: 合规要求
      description: 涉及法规合规的推理（PCI-DSS、GDPR等）
      priority: high
      subscribed: true
    payment-flow:
      name: 支付流程
      description: 涉及支付路由、清结算的推理
      priority: high
      subscribed: true
    perf-impact:
      name: 性能影响
      description: 影响性能的设计选择推理
      priority: medium
      subscribed: true
    data-model:
      name: 数据模型
      description: 数据结构设计相关推理
      priority: medium
      subscribed: true
    idempotency:
      name: 幂等性
      description: 涉及操作幂等性保证的推理
      priority: medium
      subscribed: true
    retry-strategy:
      name: 重试策略
      description: 涉及失败重试和补偿的推理
      priority: medium
      subscribed: true
    migration:
      name: 迁移策略
      description: 数据或系统迁移相关推理
      priority: low
      subscribed: true
    monitoring:
      name: 可观测性
      description: 日志、监控、告警相关推理
      priority: low
      subscribed: true

  业务:
    biz-rule:
      name: 业务规则
      description: 涉及业务流程、领域逻辑的推理
      priority: high
      subscribed: true
    ux-assumption:
      name: UX假设
      description: 关于用户体验的假设推理
      priority: medium
      subscribed: false

  通用:
    scope-decision:
      name: 范围决策
      description: 关于功能范围边界的推理
      priority: medium
      subscribed: true
```

此示例展示了金融支付项目的分类定制：新增了 `compliance`、`payment-flow`、`idempotency`、`retry-strategy`，将 `compliance` 和 `payment-flow` 设为 high 优先级，`monitoring` 从未订阅改为订阅。新增分类建议根据推理内容设置合适的 `artifacts` 和 `guess` 字段。
