# 技术集成方案

## 安装与分发

### 方式一：全局 Claude Code Skill（推荐）

类似 `guess-governance` 的安装方式，安装到用户的全局 skills 目录：

```
~/.claude/skills/reasoning-annotate/
└── skill.md
```

分类表放在全局 OpenSpec 配置目录：

```
~/.openspec/
└── reasoning-categories.yaml          ← 全局默认分类表
```

**优点**：
- 一次安装，所有项目生效
- 不需要修改 OpenSpec 源码
- 与 guess-governance 模式一致，用户熟悉

### 方式二：项目级 Skill + 项目级分类表

安装在项目的 `.claude/skills/` 或 `.agents/skills/` 目录，分类表放在 OpenSpec 目录：

```
my-project/
├── .claude/skills/reasoning-annotate/
│   └── skill.md
├── openspec/
│   ├── config.yaml
│   ├── reasoning-categories.yaml     ← 项目级分类表
│   ├── changes/
│   └── specs/
└── ...
```

**优点**：
- 随项目版本控制，团队共享
- 分类表与 OpenSpec 制品同目录，易于发现
- 与 config.yaml 同级，结构一致

### 方式三：OpenSpec 内置 Skill（未来）

在 OpenSpec 的 skill 模板系统中注册（需修改 OpenSpec 源码）：

```typescript
// repos/openspec/src/core/shared/skill-generation.ts
export function getSkillTemplates(workflowFilter?: readonly string[]): SkillTemplateEntry[] {
  const all: SkillTemplateEntry[] = [
    // ... 现有 skills
    { template: getReasoningAnnotateSkillTemplate(), dirName: 'openspec-reasoning-annotate', workflowId: 'reasoning-annotate' },
  ];
  // ...
}
```

**现状**：此方案需要 OpenSpec 上游接受合并，目前不做。优先使用方式一或方式二。

### 不嵌入 OpenSpec config.yaml 的原因

OpenSpec 的 `config.yaml` 通过 `ProjectConfigSchema`（Zod schema）校验，只接受 `schema`、`context`、`rules` 三个字段（`project-config.ts:19-41`）。添加自定义字段会导致校验失败。独立文件避免了此问题。

## 触发机制

### Auto-Trigger 通过 Description 匹配

skill.md 的 YAML frontmatter `description` 字段被 AI harness 用于 auto-trigger 匹配。当前设计：

```yaml
description: Annotate high-value AI reasoning in OpenSpec proposal and design artifacts using a user-AI co-maintained YAML classification table. Use when generating or reviewing OpenSpec proposals or designs to highlight reasoning that matches subscribed categories. Non-blocking — annotations only, never halts workflow.
```

**匹配关键词**：
- `annotate` / `标注`
- `reasoning` / `推理`
- `OpenSpec proposals` / `OpenSpec 提案`
- `classification table` / `分类表`

**预期触发场景**：
1. 用户运行 `/opsx:propose` 生成提案后
2. 用户说"标注这个提案的推理内容"
3. 用户说"检查 proposal.md 的推理亮点"
4. 用户说"review the reasoning in the design"

### 显式触发

用户也可以直接调用：
- `/reasoning-annotate` — 对当前 change 的 proposal.md 执行标注
- `/reasoning-annotate suggest` — 基于未匹配推理建议新分类

## YAML 加载实现

### AI Agent 读取流程

```bash
# 1. 检查项目级（与 config.yaml 同级）
if [ -f "openspec/reasoning-categories.yaml" ]; then
  cat openspec/reasoning-categories.yaml
# 2. 检查全局级
elif [ -f "$HOME/.openspec/reasoning-categories.yaml" ]; then
  cat "$HOME/.openspec/reasoning-categories.yaml"
# 3. 使用内置默认
else
  echo "NO_FILE"
fi
```

AI agent 读取 YAML 后，在内存中解析为分类列表：
1. 遍历 `domains` 下每个 domain
2. 遍历 domain 下每个 `category_id`
3. 过滤 `subscribed: true` 的条目
4. 将 `domain`、`category_id`、`name`、`description`、`priority` 存入分类列表
5. 用于后续匹配

### 加载示例

假设项目级 YAML 内容：

```yaml
domains:
  技术:
    arch-decision:
      name: 架构决策
      description: 涉及系统架构选择和权衡的推理
      priority: high
      subscribed: true
    security:
      name: 安全考量
      description: 安全相关的设计推理
      priority: high
      subscribed: false
  业务:
    biz-rule:
      name: 业务规则
      description: 涉及业务流程、领域逻辑的推理
      priority: high
      subscribed: true
```

AI 解析后的活跃分类列表：

| domain | category_id | name | description | priority |
|--------|------------|------|-------------|----------|
| 技术 | arch-decision | 架构决策 | 涉及系统架构选择和权衡的推理 | high |
| 业务 | biz-rule | 业务规则 | 涉及业务流程、领域逻辑的推理 | high |

（`security` 因 `subscribed: false` 被过滤）

## 标注输出格式详解

标注策略为纯 Strategy A：直接追加 `## Reasoning Annotations` section 到产物文件末尾。proposal.md 和 design.md 各自追加独立的标注 section。

### 追加到 proposal.md 的格式

在 `proposal.md` 末尾自动追加（无需用户确认）：

```markdown
<!-- reasoning-annotate: auto-generated — openspec/reasoning-categories.yaml -->
## Reasoning Annotations

**Classification source**: `openspec/reasoning-categories.yaml`
**Categories active**: 7 / 10
**Annotations found**: 5

### Summary by Domain
| Domain | Categories matched | Annotation count |
|--------|-------------------|-----------------|
| 技术   | arch-decision, security, data-model, integration | 4 |
| 业务   | — | 0 |
| 通用   | scope-decision | 1 |

### Coverage metrics
- Reasoning passages detected: 8
- Matched to subscribed categories: 5
- Unmatched passages: 3
- Coverage rate: 62.5%

---

### arch-decision ⬆️ HIGH
**Location**: "## What Changes > ### 1. Add authentication middleware"
> Choosing JWT over session-based auth because the service is stateless and needs to scale horizontally without shared session storage

### security ⬆️ HIGH
**Location**: "## What Changes > ### 3. Token refresh strategy"
> Access tokens expire after 15 minutes; refresh tokens are stored as HttpOnly cookies with SameSite=Strict

### data-model ◉ MEDIUM
**Location**: "## What Changes > ### 2. User store design"
> User profile stored in separate service to decouple auth data from business data

### integration ◉ MEDIUM
**Location**: "## Impact"
> OAuth provider integration requires callback URL configuration in each environment

### scope-decision ◉ MEDIUM
**Location**: "## Impact"
> MFA and social login deferred to Phase 2
<!-- /reasoning-annotate -->
```

### 追加到 design.md 的格式

在 `design.md` 末尾自动追加，格式与 proposal.md 一致但侧重设计决策推理：

```markdown
<!-- reasoning-annotate: auto-generated — openspec/reasoning-categories.yaml -->
## Reasoning Annotations

**Classification source**: `openspec/reasoning-categories.yaml`
**Categories active**: 7 / 10
**Annotations found**: 3

### Summary by Domain
| Domain | Categories matched | Annotation count |
|--------|-------------------|-----------------|
| 技术   | arch-decision, data-model, integration | 3 |
| 业务   | — | 0 |
| 通用   | — | 0 |

### Coverage metrics
- Reasoning passages detected: 5
- Matched to subscribed categories: 3
- Unmatched passages: 2
- Coverage rate: 60%

---

### arch-decision ⬆️ HIGH
**Location**: "## Technical Design > ### Architecture"
> Using event-driven architecture with message queue for decoupled communication between auth service and user service

### data-model ◉ MEDIUM
**Location**: "## Technical Design > ### Data Model"
> User credentials stored in separate encrypted table with one-way hash, not alongside profile data

### integration ◉ MEDIUM
**Location**: "## Technical Design > ### External Dependencies"
> OAuth providers abstracted behind adapter interface to allow adding/removing providers without core changes
<!-- /reasoning-annotate -->
```

### 替换已有 section

如果产物文件中已存在 `## Reasoning Annotations` section（由之前的标注生成），**整体替换**，不合并。识别标记为 `<!-- reasoning-annotate:` 开头、`<!-- /reasoning-annotate -->` 结尾的块。

### 会话内通知

追加完成后，在会话中输出一行摘要：

```
Appended 5 reasoning annotations to proposal.md (source: openspec/reasoning-categories.yaml, coverage: 62.5%)
```

不输出完整标注列表到会话。产物文件是唯一真相来源。

## 与 guess-governance 的协作

### 共存场景

当两个 skill 同时安装时，它们在同一提案产物上各自执行：

```
OpenSpec propose 流程
    │
    ├── guess-governance
    │   ├── 提取 Facts / Assumptions / Decisions Needed
    │   ├── 计算 Guess Ratio / Risk
    │   ├── 可能阻断（>35% ratio）
    │   └── 嵌入 governance section 到 proposal.md
    │
    └── reasoning-annotate
        ├── 加载 YAML 分类表
        ├── 扫描 proposal.md 和 design.md 的推理段落
        ├── 匹配订阅分类
        └── 直接追加 `## Reasoning Annotations` section
```

### 信息流

- guess-governance 的 Assumptions 表中的条目可作为 reasoning-annotate 的输入
- reasoning-annotate 识别的推理段落中，guess-governance 的 L3 items 应自动标记为安全相关（如果 security 分类已订阅）
- 两者互不修改对方的产物

## 局限性与风险

| 局限 | 影响 | 缓解措施 |
|------|------|---------|
| YAML 解析依赖 AI 理解，非程序化 | 复杂 YAML 结构可能解析错误 | 保持 YAML 结构简单，每层只有一层嵌套 |
| Auto-trigger 可能不准确 | 可能不触发或误触发 | description 中包含足够多的触发关键词 |
| 分类匹配主观性强 | 不同 AI session 可能匹配结果不一致 | 提供足够清晰的 description 字段 |
| 不支持跨 artifact 追踪 | 只标注单个文件内的推理，proposal.md 和 design.md 各自独立 | 未来可扩展为 change 级别汇总 |
| 与 guess-governance 的 Assumptions 重叠 | 同一段内容可能被两个 skill 重复标注 | 明确分工：governance 管"假设"，annotate 管"推理" |
| design.md 推理深度 | design.md 中的推理通常比 proposal.md 更技术化，匹配可能遗漏 | 内置默认分类包含 data-model、integration 等技术分类覆盖 |

## 后续增强方向

1. **分类表管理命令**：`/reasoning-annotate manage` 交互式编辑 YAML
2. **跨 change 统计**：汇总多个 proposal 的标注趋势
3. **OpenSpec 内置集成**：提交到 OpenSpec 上游作为可选 skill
4. **分类模板市场**：预设不同领域的 YAML 模板（金融、电商、SaaS 等）
5. **标注持久化存储**：JSON 格式的标注历史，支持趋势分析
6. **config.yaml 集成**：未来 OpenSpec schema 扩展后，支持在 config.yaml 中引用分类表路径
