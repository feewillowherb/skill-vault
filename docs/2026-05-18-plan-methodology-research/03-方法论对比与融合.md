# 方法论对比与融合设计

## 1. 设计哲学对比

### 1.1 根本差异

| 维度 | Cursor Plan | BMAD-METHOD |
|------|-------------|-------------|
| 设计哲学 | 即时性规划（Just-in-Time Planning） | 全周期规划（Full Lifecycle Planning） |
| 核心隐喻 | 现场指挥官：快速侦察 → 制定方案 → 立即执行 | 建筑事务所：概念设计 → 详细图纸 → 施工计划 → 分步建造 |
| 知识管理 | 隐式、临时性 | 显式、持久化 |
| 人类角色 | 审批者（Approver） | 协作者（Collaborator） |
| AI 角色 | 助手（Assistant） | 引导者（Facilitator） |

### 1.2 哲学光谱

```
即时性 ←————————————————————————————→ 结构化
  Cursor Plan                              BMAD-METHOD

轻量级 ←————————————————————————————→ 重量级
  Cursor Plan                              BMAD-METHOD

隐式上下文 ←————————————————————————→ 显式上下文
  Cursor Plan                              BMAD-METHOD

单一角色 ←——————————————————————————→ 多角色系统
  Cursor Plan                              BMAD-METHOD

IDE内嵌 ←———————————————————————————→ 独立框架
  Cursor Plan                              BMAD-METHOD
```

### 1.3 "AI 思考" vs "引导人类思考"

这是两种方法论最核心的哲学分歧：

**Cursor Plan**: AI 生成计划 → 人类审批 → AI 执行
- AI 是主要的思考者
- 人类是质量守门人
- 快速、高效、依赖 AI 能力

**BMAD-METHOD**: AI 引导 → 人类思考 → AI 记录 → 人类决策
- AI 是引导者和记录者
- 人类是主要思考者
- 深度、创造性强、依赖人类判断力

## 4. 融合设计建议

### 4.1 融合原则

取两者之长，构建一个**自适应的分级规划系统**：

```
核心洞察:
  Cursor Plan 的"即时规划"适合编码现场的小决策
  BMAD-METHOD 的"全周期规划"适合产品级的复杂项目

融合方向:
  根据任务复杂度自动选择规划深度
  在轻量级和重量级之间动态切换
```

### 4.2 分级规划架构

```
Level 0: 即时执行（无规划）
  适用: 简单修改、格式化、文档更新
  模式: 直接执行，无需规划

Level 1: 快速规划（Cursor Plan 风格）
  适用: 函数级开发、Bug 修复、小功能
  模式: Plan → Approve → Execute
  特点: 内嵌对话、即时性、无持久化

Level 2: 结构化规划（轻量 BMAD）
  适用: 模块级功能、跨文件重构
  模式: Quick Analysis → Plan → Review → Implement
  特点: 生成计划文档、支持回溯、轻量门控

Level 3: 全周期规划（完整 BMAD）
  适用: 新产品、大型架构、多模块系统
  模式: Analysis → PRD → Architecture → Stories → Sprint
  特点: 完整制品、角色系统、门控机制
```

### 4.3 自适应切换机制

```python
# 伪代码：任务复杂度评估
def determine_planning_level(task):
    score = 0

    # 影响范围评估
    affected_files = estimate_affected_files(task)
    if affected_files <= 3:   score += 1  # 小范围
    elif affected_files <= 10: score += 2  # 中范围
    else:                      score += 3  # 大范围

    # 跨模块评估
    affected_modules = estimate_affected_modules(task)
    if affected_modules == 1:  score += 0  # 单模块
    elif affected_modules <= 3: score += 1  # 少量跨模块
    else:                       score += 2  # 大量跨模块

    # 架构影响评估
    if involves_api_change(task):      score += 1
    if involves_db_change(task):       score += 1
    if involves_new_dependency(task):  score += 1

    # 映射到规划级别
    if score <= 1:  return Level_0  # 即时执行
    if score <= 3:  return Level_1  # 快速规划
    if score <= 5:  return Level_2  # 结构化规划
    return Level_3                  # 全周期规划
```

### 4.4 上下文管理融合

```
融合设计：双轨上下文管理

轨道1：隐式上下文（来自 Cursor Plan）
  ├── IDE 代码库索引
  ├── 打开文件和光标位置
  ├── @引用和对话历史
  └── 用途：Level 0-1 的即时性上下文

轨道2：显式上下文（来自 BMAD-METHOD）
  ├── 项目上下文文件 (project-context.md)
  ├── 决策日志 (.decision-log.md)
  ├── 阶段制品文件 (PRD, Architecture, Story)
  └── 用途：Level 2-3 的持久化上下文

融合点：
  当 Level 1 升级到 Level 2 时，将隐式上下文显式化
  当 Level 3 降级到 Level 1 时，从制品中提取关键上下文
```

### 4.5 角色系统融合

```
融合设计：弹性角色系统

Level 0-1：无角色（单一 Agent）
  单一 Agent 覆盖所有角色

Level 2：轻量角色
  ├── 规划者（合并 PM + Architect）
  └── 实现者（合并 Dev + QA）

Level 3：完整角色
  ├── Mary (BA)        → 分析阶段
  ├── John (PM)        → 规划阶段
  ├── Sally (UX)       → 规划阶段
  ├── Winston (Arch)   → 方案设计阶段
  ├── Amelia (Dev)     → 实施阶段
  └── Paige (TW)       → 跨阶段文档
```

## 5. 总结

### 5.1 核心洞察

| 洞察 | 描述 |
|------|------|
| 即时 vs 全周期 | 不是非此即彼，而是不同场景需要不同深度的规划 |
| 隐式 vs 显式 | 上下文管理应该根据任务复杂度选择策略 |
| 单一 vs 多角色 | 角色专业化是手段而非目的，简单任务不需要多角色 |
| 审批 vs 协作 | 人机关系应该在"监督"和"共创"之间动态调整 |
