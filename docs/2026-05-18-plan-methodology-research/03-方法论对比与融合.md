# BMAD-METHOD 分析与自适应分级规划设计

## 1. BMAD-METHOD 设计哲学

### 1.1 核心理念

| 维度 | BMAD-METHOD |
|------|-------------|
| 设计哲学 | 全周期规划（Full Lifecycle Planning） |
| 核心隐喻 | 建筑事务所：概念设计 → 详细图纸 → 施工计划 → 分步建造 |
| 知识管理 | 显式、持久化 |
| 人类角色 | 协作者（Collaborator） |
| AI 角色 | 引导者（Facilitator） |

### 1.2 "引导人类思考"模式

**BMAD-METHOD**: AI 引导 → 人类思考 → AI 记录 → 人类决策
- AI 是引导者和记录者
- 人类是主要思考者
- 深度、创造性强、依赖人类判断力

## 4. 自适应分级规划设计

### 4.1 设计动机

BMAD-METHOD 提供完整的全周期规划框架，但对中小型任务存在过重的问题：

- **学习曲线陡峭**: 六角色系统和四阶段生命周期对新手不友好
- **制品冗余**: 小型任务不需要完整的 PRD + Architecture + Story 制品体系
- **上下文开销**: 文件化传递对函数级修改增加了不必要的流程

需要构建一个**自适应分级规划系统**，在保持 BMAD 核心优势的同时，为不同复杂度的任务提供匹配的规划深度。

### 4.2 分级规划架构

```
Level 0: 即时执行（无规划）
  适用: 简单修改、格式化、文档更新
  模式: 直接执行，无需规划

Level 1: 快速规划
  适用: 函数级开发、Bug 修复、小功能
  模式: Research → Plan → Approve → Execute
  特点: 即时性、无持久化制品

Level 2: 结构化规划（轻量 BMAD）
  适用: 模块级功能、跨文件重构
  模式: Quick Analysis → Plan → Review → Implement
  特点: 生成计划文档、支持回溯、轻量门控

Level 3: 全周期规划（完整 BMAD）
  适用: 新产品、大型架构、多模块系统
  模式: Analysis → PRD → Architecture → Stories → Sprint
  特点: 完整制品、角色系统、门控机制
```

### 4.3 自适应切换机制

```python
# 伪代码：任务复杂度评估
def determine_planning_level(task):
    score = 0

    # 影响范围评估
    affected_files = estimate_affected_files(task)
    if affected_files <= 3:   score += 1  # 小范围
    elif affected_files <= 10: score += 2  # 中范围
    else:                      score += 3  # 大范围

    # 跨模块评估
    affected_modules = estimate_affected_modules(task)
    if affected_modules == 1:  score += 0  # 单模块
    elif affected_modules <= 3: score += 1  # 少量跨模块
    else:                       score += 2  # 大量跨模块

    # 架构影响评估
    if involves_api_change(task):      score += 1
    if involves_db_change(task):       score += 1
    if involves_new_dependency(task):  score += 1

    # 映射到规划级别
    if score <= 1:  return Level_0  # 即时执行
    if score <= 3:  return Level_1  # 快速规划
    if score <= 5:  return Level_2  # 结构化规划
    return Level_3                  # 全周期规划
```

### 4.4 上下文管理设计

```
分级上下文管理：

Level 0-1：轻量上下文
  ├── IDE 代码库索引
  ├── 打开文件和光标位置
  ├── @引用和对话历史
  └── 用途：即时性上下文，会话级生命周期

Level 2-3：显式上下文（来自 BMAD-METHOD）
  ├── 项目上下文文件 (project-context.md)
  ├── 决策日志 (.decision-log.md)
  ├── 阶段制品文件 (PRD, Architecture, Story)
  └── 用途：持久化上下文，项目级生命周期

级别转换：
  Level 1 → Level 2: 将轻量上下文关键信息显式化写入文件
  Level 3 → Level 1: 从制品中提取摘要作为对话上下文注入
```

### 4.5 角色系统设计

```
弹性角色系统：

Level 0-1：无角色（单一 Agent）
  单一 Agent 覆盖所有角色

Level 2：轻量角色
  ├── 规划者（合并 PM + Architect）
  └── 实现者（合并 Dev + QA）

Level 3：完整角色
  ├── Mary (BA)        → 分析阶段
  ├── John (PM)        → 规划阶段
  ├── Sally (UX)       → 规划阶段
  ├── Winston (Arch)   → 方案设计阶段
  ├── Amelia (Dev)     → 实施阶段
  └── Paige (TW)       → 跨阶段文档
```

## 5. 总结

### 5.1 核心洞察

| 洞察 | 描述 |
|------|------|
| 规划深度应匹配复杂度 | 不同场景需要不同深度的规划，而非一律采用全周期流程 |
| 显式上下文的价值 | BMAD 的文件化上下文传递在复杂项目中优势明显，但在简单任务中是开销 |
| 角色专业化是手段 | 角色系统应按需激活，简单任务不需要多角色 |
| 自适应是关键 | 系统应能根据任务自动推荐合适的规划深度 |
